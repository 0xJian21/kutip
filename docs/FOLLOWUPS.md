# Follow-ups after Session 7

Known gaps left open on purpose (2026-09-27). Each has where, what goes wrong, and the fix. Tick them off as they land.

Session 8d (2026-09-29) closed this list for demo day: every item is either ticked with what landed, or marked **won't fix** with the reason. The 8d security review's own findings are at the end.

## From the final code review (minor)

- [x] **Submit route can mark an unrelated action executed.** (8b: `agent_actions.proposal_index` + `store.settleProposal`, only `proposed` rows for that index.) `apps/web/app/api/treasury/proposals/[index]/submit/route.ts` sets `actionId` to `executed` with the signature without checking that the action is `proposed` and belongs to proposal `#index`. An owner could overwrite the audit trail of a rejected action or an escalation. Fix: require `status = 'proposed'` and `inputSummary` starting with `proposal #<index>` (better: an `agent_actions.proposal_index` column).
- [x] **Raw error messages can reach the browser.** (8b: `UserError`; everything else → "Something went wrong".) `apps/web/lib/data/result.ts` only masks errors starting with "Failed query". Postgres connection errors (Supabase project ref), `Privy user lookup: HTTP 401`, Anthropic SDK errors and `exporter not found: …` are shown as they are, and a thrown non-Error crashes `err.message.startsWith`. Fix: a `UserError` class for messages meant for users; everything else becomes "Something went wrong".
- [x] **PDF size limit vs Vercel.** (8b: 4 MB in the action and `bodySizeLimit`; the client hint in `new-invoice.tsx` still says 8 MB → 8a.) `lib/data/actions.ts` allows 8 MB and `next.config.ts` sets `bodySizeLimit: "10mb"`, but Vercel functions cap request bodies at 4.5 MB, so a 4.5–8 MB PDF gets a platform 413 instead of the friendly message. Fix: cap at 4 MB in the client and the action.
- [x] **Realtime can switch off silently.** (8b: `next.config.ts` warns at build time.) `apps/web/next.config.ts` maps `SUPABASE_URL` / `SUPABASE_ANON_KEY` into `NEXT_PUBLIC_*` at build time. If they are missing in the Vercel build, live updates quietly stop. Fix: fail the build or log a warning when they are empty.
- [x] **Mock mode in production bypasses auth on treasury routes.** (8b: `MOCK` is false when `NODE_ENV=production`; `treasuryContext()` throws in mock.) With `NEXT_PUBLIC_KUTIP_MOCK=1`, `getSession()` returns a demo session with no cookie, and `/api/treasury/*` still uses the real DB and fee payer. Fix: ignore `MOCK` when `NODE_ENV === "production"`, or make `treasuryMultisig()` throw in mock mode.
- [x] **Reused screenings leave no per-invoice record.** (8b: a row per invoice, reasons name the reused screening.) `app/api/pay/[invoiceId]/route.ts` records a screening row only for fresh screens, so the compliance trail can't show which check covered which invoice. Fix: record a row pointing at the reused screening.
- [x] **Mock fixtures ship to the browser.** **Won't fix (8d):** the fixtures are the fictional demo data the seed also loads (no secrets, nothing real), so this costs bundle size only; the five importing client components are in 8a's restyle lane. Client components import `@/lib/mock` statically. Fix later: dynamic import only when `MOCK` is on.
- [x] **`/treasury-test` is public in production.** (8b: removed; MFA enrolment lives under Settings → Agent permissions.) It is a `(dev)` route. Fix: `notFound()` unless `NEXT_PUBLIC_DEMO_CONTROLS=1`, or move MFA enrolment into Settings.
- [x] **`demo-reset` seed is not transactional.** (8d: the seed runs in-process and steps 1–4 are one transaction; checked against a local Postgres with an injected failure in step 4, which left the previous demo state untouched.) The seed ran as a child process. A failure after step 1 left placeholder multisig addresses until a re-run.

## Behaviour to know about

- [x] **Provisional screening pass.** (8d: kept as designed; x402 payers now go through the same gate, `screenPayer` in `app/api/pay/_lib/server.ts`.) A wallet-history check that runs over 2.5 s lets the payment through and finishes afterwards (your requirement). A bad late result escalates (rule T1), and the recorded flag now blocks that wallet from then on. Only its first attempt can still get a transaction built. Revisit if a judge's wallet ever shows up as flagged.
- [x] **`after()` lifetime on Vercel.** (8d: checked, no move needed. The Vercel project has Fluid compute on with a 300 s default function timeout (`vercel api /v9/projects/kutip`), so a 12–37 s late screen finishes inside the same invocation.) The late screening runs in `after()`. If the function hit its max duration first, the verdict would be lost silently.
- [x] **Per-instance caches on serverless.** **Won't fix (8d):** safe by construction. What costs money is now capped across instances where it matters: onboarding counts exporters in the DB, pay-page messages lock the invoice row, x402 has one settlement in flight per invoice per instance plus CU caps. `InFlight`, `LiveTxCache` and the rate limiters live per Vercel instance, so parallel wallet POSTs that land on different instances can build two transactions. Safe (keys include invoice, wallet and token), just less deduplication.
- [x] **Worker catch-up looks at the last 20 signatures per reference.** **Won't fix (8d):** the gRPC stream is the primary path, and dust on a reference no longer blocks catch-up, since each signature is isolated (one that fails to fetch or record is logged and skipped). A reference flooded with more than 20 dust transactions could hide a real payment from catch-up. The gRPC stream is still the primary path.
- [x] **Rejecting a Squads proposal only updates the database.** (8b: `proposalReject` signed by the owner via `/api/treasury/proposals/[index]/reject` + submit `decision: "rejected"`. Rent of rejected/executed proposal accounts is still not reclaimed: `vaultTransactionAccountsClose` from a script later.) The on-chain proposal stays Active. Fix: add a `proposalReject` owner transaction, or cancel stale proposals from a script.
- [x] **Sign-in requires a linked Kutip user.** (8b: unlinked sign-ins go through onboarding and get their own exporter + a real treasury, ≈ 0.004 SOL from the fee payer each, capped at 5/hour/instance and paused under 0.02 SOL. With `DEMO_FALLBACK=1` they land in the demo exporter instead. Decide which you want for judges.)
- [x] **Resend test sender.** **Won't fix for the demo (8d):** no domain (owner decision, IMPROVEMENTS E2). Demo buyers' emails are the owner's inbox. It only delivers to `jianwei2102@gmail.com` exactly (no `+aliases`, no other people). To email real buyers, verify a domain in Resend and set `EMAIL_FROM` on Fly and Vercel.
- [x] **Receipt wording.** (Fixed in `f24f861`: the facts carry `longDate()` ("27 September 2026") and the style rule says "never in digits only, never spelled out".) Haiku wrote the date as "twenty-seventh September two thousand twenty-six" in a receipt (`packages/agent/src/writer.ts`).
- [x] **Privy allowed origins.** (8d, read from Privy's public app config: allowed domains `https://kutip-app.vercel.app` and `http://localhost:3100`; passkey + email login on; passkeys for sign-up on; MFA method passkey.) Local dev on another port needs that origin added in the dashboard.

## Session 8d security review (2026-09-29)

Three read-only reviews of `main` at `6f0bcdf` covered auth/session/server actions/treasury, the public pay/x402/messages surface, and agent/Realtime/RLS/bundles/worker. What was fixed on `feat/hardening`:

- [x] **High: an owner could get the fee payer to co-sign a drain.** Any self-onboarded owner is a full member of their own multisig and could create a Squads vault transaction naming the fee payer, then POST `/api/treasury/proposals/[n]/approve`. Execute passes inner accounts through, and a signer flag is per transaction. Now `approveExecuteInstructions` requires creator = Kutip's agent, one USDC transfer out of the treasury vault ATA, and no fee-payer account, and `buildOwnerTx` runs `assertFeePayerAbsent` (Squads rent payer allowed only for the permissions config txs).
- [x] **High: x402 fee drain with txs that pass simulation and fail on-chain.** Added per-invoice and per-IP limits, one settlement in flight per invoice, a 10-minute cooldown for a payer whose co-signed tx failed, and CU caps of 200k at 10k µL (a failed settle costs ≤ ~12k lamports).
- [x] **Medium: x402 payers weren't screened.** They now go through the same sanctions + history gate as Solana Pay.
- [x] **Medium: raw errors to the browser.** x402 verify/send errors (web3.js fetch errors carry the RPC URL + key) and the four treasury routes now return fixed messages; details are logged.
- [x] **Medium: the read-only `demo` role could write.** Rulebook, decisions, invoices, reminders, replies, drafts and logged messages all need `writeSessionOrThrow`.
- [x] **Medium: LLM spend and command-bar reminder size weren't capped.** 60 agent calls/hour/exporter (per instance); reminder body ≤ 4,000, subject ≤ 200.
- [x] **Medium: onboarding cap per instance with a race.** Now a DB count across instances plus a slot reserved before any await. The create key comes from the owner wallet, so a retry reuses the multisig.
- [x] **Medium: cash-out proposal spam locked fee-payer rent.** One open cash-out proposal per exporter.
- [x] **Medium: pay-page message rate limit was check-then-insert.** 12 parallel posts all landed. Now one transaction with a row lock (5 land); the IP comes from `x-real-ip`.
- [x] **Medium: an automatic reply could carry injected content.** `autoSendProblem` refuses foreign links, domains, emails, long numbers, bank/chat wording and other invoice numbers before a routine reply goes out (it becomes a draft). The buyer context leaves out draft invoices.
- [x] **Low, fixed:** worker catch-up aborted on one bad signature; `RateLimiter` never dropped keys.

Low, left open (documented, not demo-blocking):
- [ ] Signed Touch ID statements can be replayed within their 10-minute window by someone who also holds the session cookie (store used signatures to close it).
- [ ] `permissionsSave` stores the client-sent `spendingLimitPda` without recomputing it (self-harm only; the sweeper would fail rather than overspend, since the on-chain limit is the guard).
- [ ] Sessions can't be revoked before their 12 h expiry (role and wallet are baked into the cookie).
- [ ] `logoUploadForSignup` has no per-user quota (512 KB each, raster types only).
- [ ] Solana Pay: a buyer can sign and submit a fee-payer-signed tx after moving their funds away (≈ 10–24k lamports per attempt; per-invoice limit 10/min per instance, and fresh wallets are flagged by screening).
- [ ] The `invoice:<id>` payment broadcast includes the payer wallet. It is public on Solscan from the signature the pay page shows anyway.
- [ ] Anyone can publish on the public broadcast topics. The owner UI applies an `invoice` payload before its refetch, so a spoofed "paid" can flash until the refetch lands. Fix: refetch only (8a/UI lane).
- [ ] One pay-page message the classifier reads as a dispute sets the invoice `disputed`, which stops `/api/pay` and x402 (409) until the owner acts. By design (C4), but anyone with the link can do it.
- [ ] Zero-value transactions naming a reference flip `sent` → `seen`.
- [ ] `replyAutonomy` in `rulebook.ts` is unused (the inbox enforces `replyPermission`); delete it later.

## Later (after the hackathon)

- [ ] **Move to Singapore, all together or not at all.** The database decides where the servers go: Supabase is in ap-northeast-1 (Tokyo), so Vercel (`hnd1`) and Fly (`nrt`) sit next to it. Moving only the servers to Singapore would add ~70 ms to every DB round trip, and pages make 5–9 of them. For Malaysian users, create a Supabase project in `ap-southeast-1`, run `db:migrate` and `demo-reset`, swap `DATABASE_URL` / `SUPABASE_URL` / `SUPABASE_ANON_KEY` in `.env`, Vercel and Fly, then set Vercel `regions: ["sin1"]` and Fly `primary_region = "sin"`. Gain: ~60 ms faster page loads from KL.
